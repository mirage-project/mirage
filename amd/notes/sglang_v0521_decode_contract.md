read directly in code.

Terms used throughout:
* **bs** = number of requests in the decode step; each request contributes exactly one new token, so the step has bs token rows.
* **captured size** = a batch size for which SGLang recorded a HIP graph (a CUDA-graph equivalent on ROCm) at startup.
* **padded row** = a row added to fill a real batch up to the next captured size; it belongs to no request.
* **slot** = row index of a request's KDA state in the per-layer state pools (`mamba_cache_indices`).
* **KV slot** = row index of one token's MLA latent KV row in the per-layer KV buffer (`out_cache_loc`, `req_to_token` entries).
* **stable under replay** = the tensor is allocated once and refreshed in place before every replay, so a captured kernel may bind
  its address at capture time.

## A. Forward mode, batch, graphs, padding

### A.1 Mode and token count

* The scheduler sets `ForwardMode.DECODE` in `ScheduleBatch.prepare_for_decode` (`srt/managers/schedule_batch.py:3538-3539`);
  the spec branch (3554-3562) is not taken without `--speculative-algorithm`.
* One token per request: `alloc_for_decode(self, token_per_req=1)` (`schedule_batch.py:3580`); the graph runner's per-request
  width is `decode_num_tokens_per_req()` = 1 for non-spec, non-dLLM (`srt/model_executor/model_runner.py:827-848`, used at
  `srt/model_executor/runner/decode_cuda_graph_runner.py:303-305`). Token rows per forward = bs (padded bs under a graph,
  `decode_cuda_graph_runner.py:1412-1418`).
* Capture mode is `ForwardMode.DECODE` (`decode_cuda_graph_runner.py:300`; only spec draft workers switch to TARGET_VERIFY,
  306-311).
* Mode predicates: `is_decode()` and `is_decode_or_idle()` are True, `is_extend()` and `is_target_verify()` are False
  (`srt/model_executor/forward_batch_info.py:224-258`).

### A.2 Captured sizes for `--cuda-graph-max-bs-decode 64`

* `cuda_graph_max_bs_decode` sets `decode.max_bs = 64` (`srt/arg_groups/cuda_graph_hook.py:77-78`); the list is generated by
  `generate_decode_cuda_graph_batch_sizes` (`cuda_graph_hook.py:624-656`, called from `srt/arg_groups/memory_hook.py:192-196`).
  Non-spec branch: `[1, 2, 4, 8, 12] + range(16, 257, 8) + ...`, cut at 64 (633-640, 651).
* Filter in `get_batch_sizes_to_capture` (`srt/model_executor/runner/base_cuda_graph_runner.py:64-93`): alignment = 1 without
  two-batch overlap and without gathered buffers (`srt/utils/common.py:4229-4238`, `4195-4221`; no a2a backend, no DP attention -
  **(inferred)** from the recipe flags), and `bs <= req_to_token_pool.size` = 64.
* **Captured sizes: 1, 2, 4, 8, 12, 16, 24, 32, 40, 48, 56, 64** (12 graphs). Captured largest first (`decode_cuda_graph_runner.py:1132-1137`).
  Each size runs two eager warm-up forwards, then the capture forward (`srt/model_executor/runner_backend/full_cuda_graph_backend.py:159-173`).
* Every decode batch with bs <= 64 replays a graph (`can_run_graph`, `decode_cuda_graph_runner.py:744-748`); `--max-running-requests 64`
  keeps bs <= 64, so no eager decode forward happens in this config **(inferred)**.

### A.3 How a real batch is padded

`load_batch` (`decode_cuda_graph_runner.py:1395-1430`): padded size = smallest captured size >= raw bs (`_pad_to_bucket`,
`base_cuda_graph_runner.py:157-170`); `num_padding = bs - raw_bs` (`build_replay_fb_view`, `decode_cuda_graph_runner.py:188`).
The registry copies the live batch into rows `[0, raw_bs)` and resets the tail per slot policy
(`srt/model_executor/cuda_graph_buffer_registry.py:388-428`, policies at 572-611):

| per-row value | real row | padded row | source |
|---|---|---|---|
| `req_pool_indices` (int64) | request's row in `req_to_token` | **0** (ZERO policy; also zeroed again by `fused_replay_state_indices`) | registry 588-594; `kernels/ops/mamba/mamba_state_indices_triton.py:45-49` |
| `seq_lens` (int64) | KV length **including** the new token | **1** = `seq_len_fill_value` | registry 595-602; hybrid backend delegates to triton (`srt/layers/attention/hybrid_linear_attn_backend.py:1391-1392`), triton returns 1 (`srt/layers/attention/triton_backend.py:1353-1354`) |
| `out_cache_loc` (int64) | KV slot of the new token | **0** | registry 581-587 |
| `positions` (int64) | `clamp_position(seq_lens)` (`forward_batch_info.py:1147`) | 0 | registry 574-580; K3 has no RoPE, positions are not read by KDA/MLA **(inferred)** from verify note C |
| `input_ids` | new token id | stale (FOREACH_COPY, not reset) | registry 573; 547-548 |
| KDA slot (`mamba_cache_indices`) | `req_index_to_mamba_index_mapping[req]` | **-1** | `mamba_state_indices_triton.py:43`; reference chain `hybrid_linear_attn_backend.py:776-783` |
| KDA `query_start_loc[i]` (int32, bs+1) | i | `bs - num_padding` for every entry from `bs - num_padding` on (zero-length rows) | `hybrid_linear_attn_backend.py:871-882` |

What padded rows touch, so a kernel can process or skip them:
* `req_to_token` row 0 is a reserved all-zero padding row (`srt/mem_cache/memory_pool.py:391-400`), so a padded row's MLA KV list is
  `[req_to_token[0, 0]] = [0]`.
* MLA KV slot 0 is the reserved dummy slot (`memory_pool.py:4678-4686`); padded rows **write** their latent row there and read it back.
* KDA slot 0 is reserved too (`srt/mem_cache/allocator/mamba.py:84-87`; mapping zero-initialised, `memory_pool.py:1498-1500`), but under
  replay padded rows carry -1, and both SGLang KDA kernels skip -1 rows entirely (A.4).
* No masking downstream: `num_token_non_padded` is None outside expert parallelism (`decode_cuda_graph_runner.py:1039-1043`), so
  padded rows go through every GEMM, all-reduce and the MoE router **(inferred)** from that comment and the absence of other masks.

### A.4 Values of padded rows (consequence)

SGLang's KDA conv kernel returns before writing anything for a row whose slot is -1 (`kernels/ops/mamba/causal_conv1d_triton.py:692-695`),
and its output tensor is `torch.empty_like` (1100); the recurrence sees a zero-length row (bos == eos) and stores no output
(`kernels/ops/attention/fla/fused_sigmoid_gating_recurrent.py:225-231, 296`) into `q.new_empty` (623). So **from the first KDA layer on,
padded rows hold uninitialised values**, which then flow through o_norm, o_proj, the all-reduces, the aggregations, the MoE router and
experts **(inferred)**. A replacement kernel may write anything into padded rows' outputs, must never write state for slot -1, and must
not let a padded row's garbage (possibly NaN/Inf) index memory out of bounds (e.g. top-k ids) - whether AITER's top-k tolerates NaN
logits was not checked.

During capture and warm-up (not replay), `req_pool_indices` is all zero and `num_padding = 0`, so every row maps to KDA slot 0 and MLA
KV slot 0 (`decode_cuda_graph_runner.py:1091-1096`, `hybrid_linear_attn_backend.py:366-382`): duplicate writes into the reserved slots.

### B.3 Exact decode semantics (only where they differ from the verify note A.3)

Conv (`causal_conv1d_triton.py:715-1008`, seqlen = 1, state_len = 3):
```
c0, c1, c2 = conv[slot][0], conv[slot][1], conv[slot][2]           # bf16, oldest first
conv[slot] = [c1, c2, x]                                            # x = mixed_qkv[i] (pre-conv, bf16); shift by one
y = silu( c0*w0 + c1*w1 + c2*w2 + x*w3 )   (fp32 accumulate, w fp32, no bias)  -> stored bf16
```
Recurrence (`fused_sigmoid_gating_recurrent.py:258-528`), one step, same per-step math as verify:
```
h = temporal[slot]  (fp32; zeros if slot < 0)
g = -5 * sigmoid(exp(A_log[h]) * (a + dt_bias))        per K channel, fp32
beta = sigmoid(b)
q, k L2-normed with eps 1e-6;  q *= 128^-0.5
h *= exp(g)[k];  v -= sum_k h k;  v *= beta;  h += k (x) v;  o = sum_k h q   (o stored bf16)
temporal[slot] = h        (fp32, only if slot >= 0)
```
There is no commit step after decode: both in-place writes are final, and the next decode step reads them.

### B.4 What a replacement KDA decode kernel must do

For each real row: read `conv[slot]`, `temporal[slot]`; write `conv[slot] = [c1, c2, x]` (pre-conv bf16 inputs) and
`temporal[slot] = h_new` (fp32); output o (or the gated-normed output if o_norm is folded in). Skip rows with slot < 0 entirely (no state
write). Slots of the real rows are distinct (one slot per request) **(inferred)** from the allocator. Same rounding points as verify:
conv output rounded to bf16 before the recurrence, o rounded to bf16 before `o_norm`.

### B.5 `SGLANG_ROCM_K3_KDA_FUSED_BACKEND=aiter` (`kda_fused_decode_aiter_hip`, `defer_f_b`)

* Not in the recipe, so off by default. When set and AITER/FlyDSL support is present, `_prepare_fused_decode` stashes
  `(f_b_weight [12,128,128] bf16, o_norm weight bf16, eps, A_log)` and sets `_kda_hip_fused_decode_ready` (`kimi_k3.py:1897-1943`).
  It applies only to `is_decode()` (`defer_f_b`, 2070-2072); target verify never uses it.
* Intended replacement: the f_b GEMM (`f_a` [bs,128] -> forget gate), the conv update, the delta-rule step and the gated o_norm, as one
  FlyDSL kernel (`kda_backend.py:781-808`; op `kernels/ops/attention/kda_flydsl/kimi_k3_kda_decode.py`).
* As read, it does not engage in plain decode: `covered()` requires `raw_beta.shape == (1, batch, 12)`
  (`kernels/ops/attention/kda_fused_decode_aiter_hip.py:71`), but decode `beta` is [bs, 12] (`kimi_k3.py:2082-2085`). The backend then
  logs "K3 HIP fused KDA rejected" once (`kda_backend.py:809-826`), recomputes the forget gate with `kimi_k3_tiny_gemm(f_a, f_b_weight)`
  (839-851), and runs the unfused chain of B.1 (the generic fused stash `_k3_fused_decode_args` is not set in this mode, 1943). Same values
  as without the env var. Not checked on a running server.

### C.3 Attention kernel: which one depends on the captured size

Decision (`triton_backend.py:2274-2295`): `enable_lean_attention` default None (`exec_.py:142-145`), `SGLANG_DISABLE_LEAN_ATTENTION`
default False (`srt/environ.py:1153`); at capture `lean_capture_policy(12, 12, bs, is_mla=True)` returns `bs >= 8`
(`kernels/ops/attention/decode_attention.py:1739-1778`), and `decode_attention_fwd` takes Lean on HIP for Lk = 576
(1202-1233, 1292-1303). The choice is baked per graph:

* **Captured sizes 1, 2, 4 (real bs 1-4): grouped split-K kernel** (`decode_attention_fwd_grouped`, 1098-1155). The gfx950 MLA
  re-tuning is off (`SGLANG_MLA_DECODE_TUNE` default False, `environ.py:1175`; 159-169), so per-request split counts come from
  `get_num_kv_splits_triton` (`kernels/ops/attention/metadata.py:12-60`, called at replay prep, `triton_backend.py:1330-1332`).
  Stage 1 (511-767; BLOCK_N = 16 for Lk >= 576 on HIP, 795-797; one head tile of 12 heads, `_GROUPED_BLOCK_H` = 16): split s covers
  `ceil32(ceil(L / S))` rows; online softmax over 16-row blocks, `qk = dot(q_nope, c) + dot(q_pe, k_pe)` fp32 `* sm_scale`;
  **P.V with p rounded to bf16** (736); `e_sum` = fp32 sum of unrounded p (738); partial `acc / e_sum` stored **fp32** into
  `attn_logits`, `lse = m + log(e_sum)` fp32 (748-764). Stage 2 (905-989): fp32 LSE merge over the splits, output bf16.
  The split count S uses the batch's min and max `seq_lens`, padded rows (length 1) included (`metadata.py`), so a request's split
  geometry depends on its batch mates and on padding.
* **Captured sizes 8-64 (real bs 5-64): Lean persistent kernel** (`_decode_lean_attention_fwd`, 1940-; kernel 1391-1726): a fixed grid
  of 256 programs (one per CU, `_lean_decode_launch_params` 1916-1937; no XCD remap since 1 KV head), KV block 16 rows (1321-1330),
  work split by tiles across programs; same p-to-bf16 P.V rounding (1658); **unnormalised** fp32 partials (m, l, acc) of non-host
  programs written to `lean_Mp/Lp/Op` and merged by the host program under spin locks (1663-1715); final `acc / e_sum` -> bf16 (1720-1724).
  The reduction tree depends on how the batch's tiles fall across programs **(inferred)** from the work-stealing schedule.

`max_kv_splits` = `max(8, min(256, next_pow2(ceil(context_len / 32))))` (`triton_backend.py:317-323`, 80-87; default 8 at
`exec_.py:320-323`) = **256** with K3's `max_position_embeddings` 1048576 (`k3_config.json:171`) **(inferred)**: assumes
`context_len` = that value (no `--context-length` in the recipe).

## E. Hooks for decode, and what a captured kernel may read by pointer

### E.1 Call sites in `kimi_k3.py`

Same place as verify: `KimiK3DecoderLayer.forward` (`kimi_k3.py:2636-2659`), keep `attn_boundary.prepare` (2644-2646; aggregation 1 and
the bank row write), replace `_run_self_attn` + `attn_boundary.finish` + `ffn_boundary.prepare` (2647-2651), then the MoE call (2652-2656)
and `ffn_boundary.finish` (2659). State to leave behind is the same as verify (layer map section 3): `stream.write(u)`, no bank write.

Condition for decode: `forward_batch.forward_mode.is_decode()` and `h.shape[0] == forward_batch.batch_size`, where `batch_size` is the
**captured size** (capture builds the ForwardBatch with `batch_size=bs` of the graph, `decode_cuda_graph_runner.py:1011-1013`). Our current
`attn()` returns None in decode: it requires `is_target_verify()`, `batch_size == 1` and 8 rows (`amd/serving/sglang_k3.py:624-626`), and
`_kda_io` also requires the ReplaySSM rings (578-581), which do not exist here. Our `moe()` does run in decode on every swapped layer
(397-440): bs rows are processed in chunks of 8 with zero padding (`sglang_k3.py:428-440`), so a decode server with only `MPK_K3_MOE=run`
already uses our MoE.

Python in the hook runs only during the two warm-up forwards and the capture forward of each size (`full_cuda_graph_backend.py:159-173`)
and never during replay. Every per-step value a kernel needs must therefore come from a stable buffer (E.2); Python-side values (bank row
count, bs, block-write flag) are baked per graph, which is correct because they do not change between steps of the same size
**(inferred)** for nvb from the layer map 1.0. Per-size tensors (outputs, info words) must be created in the warm-up runs, not during capture.

## F. Every difference from the verify contract

Batch and graphs:
1. Mode `DECODE` (not `TARGET_VERIFY`): `is_decode()` True, `is_extend()` False; graphs captured in DECODE mode.
2. One token per request, bs = 1..64 requests (verify: 1 request, 8 tokens). Captured sizes 1, 2, 4, 8, 12, 16, 24, 32, 40, 48, 56, 64;
   real batches are padded up to the next one (verify: spec list, bs 1).
3. Padded rows exist: `req_pool_indices` 0, `seq_lens` 1, `out_cache_loc` 0, KDA slot -1, zero-length `query_start_loc` entries; their
   activations are uninitialised from the first KDA layer on.

KDA:
4. Kernels: `causal_conv1d_update` (seqlen 1) + `fused_sigmoid_gating_delta_rule_update` with state update, no ring, no intermediate
   buffers (verify: same two kernels with `disable_state_update=True`, ReplaySSM rings, intermediate conv window).
5. **`temporal[slot]` is written in place** (fp32 h after the token); verify leaves it untouched and a commit folds the accepted prefix.
6. **`conv[slot]` is shifted by one** (`[c1, c2, x]`); verify writes `[x5, x6, x7]` and the commit then overwrites it from the window.
7. No post-step commit, no `intermediate_conv_window`, no `verify_intermediate_state_indices` row, no ring cursor or ring positions.
8. `forget_gate` and `beta` arrive 2-D ([bs, 1536], [bs, 12]); verify: [1, 8, 12, 128] and [1, 8, 12].
9. The generic fused decode and the AITER fused decode both exist for this mode but are rejected by their shape checks
   (`b.ndim == 3`, `raw_beta.shape == (1, bs, 12)`); o_norm stays a separate op, as in verify.
10. f_b and [f_a|b] GEMMs switch from the tiny GEMM to `F.linear` above bs 12 / 16 (verify: always tiny).
11. Padded rows: slot -1 rows are skipped by both kernels (no state write, no output write).
12. Correction to the verify note A.3: `_kda_fused_decode_ready` is True on HIP without the AITER env var (`kimi_k3.py:1897-1986`); the
    verify outcome (unfused o_norm) is unchanged because the CuTe verify path that would consume it needs CUDA (`kda_backend.py:1702`).

MLA:
13. One query per request: no 8x8 draft block, no causal mask, `qo_indptr` unused (verify: 8 queries, causal within the 8).
14. `seq_lens` / `kv_indptr` **include** the new token (verify: exclude the 8 drafts).
15. The new latent row is written to the cache first and read back from the cache like every other row (verify: the 8 draft rows come
    from `k_extend` / `v_extend` registers, not from the cache).
16. Attention kernel: `decode_attention_fwd` - grouped split-K for captured sizes 1-4, Lean persistent for 8-64 (verify:
    `verify_shared_kv_fwd`). Partials are fp32 (verify: bf16-rounded split outputs); p is bf16-rounded for P.V for every key, including
    the newest (verify: fp32 p for the draft block). Split geometry depends on batch mates and padding.
17. `out_cache_loc` has bs entries (verify: 8); same row layout `[k_nope | k_pe]` bf16 and same index_put write.

MoE / boundaries:
18. MoE kernels selected by token count bs (tuned AITER rows 1, 2, 3, 4, 8, 16, 32, 64); verify always used the 8-token row.
19. o_proj all-reduce is never quantized in decode (verify: would quantize only with `--enable-quant-communications`, off).
20. No dspark capture of the stream (verify: DSPARK captures `dspark_layers_to_capture`).

Unchanged: weights and their layouts, gate formulas (`g`, `beta`), L2 norms and scale, conv output and o rounded to bf16, o_norm formula,
MLA latent/norm/absorb/gate/o_proj rounding points and scaling 192^-0.5, aggregation 1 and 2 equations, bank geometry per token row,
MoE output contract.

Not settled by this reading: (a) whether AITER's top-k and MoE kernels stay in bounds on NaN/Inf rows from padded requests; (b) the exact
`context_len` the server resolves (sets `max_kv_splits` and the `kv_indices` buffer size); (c) the AITER custom all-reduce size cap;
(d) whether the two fused-KDA rejections in B.1 / B.5 show up in a server log as read here - no server was started.
