These static schedules target the 132-SM H100 and the GPT-OSS layer graphs in this demo. They were generated by MPK's schedule solver, use 80 QKV tasks, and place the layer tasks across SMs. The output head keeps its round-robin schedule.

Batch-one decode on the same login-node H100s, with a 77-token prompt and 200 generated tokens:

| Model | Round robin | Tuned schedule | Generated tokens vs. round robin |
| --- | ---: | ---: | --- |
| GPT-OSS-20B | 3.102 ms/token | 3.055–3.073 ms/token | 200/200 identical |
| GPT-OSS-120B | 4.698 ms/token | 4.421–4.424 ms/token | 200/200 identical |

The plans are selected only for the tested H100 device name and SM count. Other devices use round robin.

With the 80-task QKV grid but round-robin placement, the same runs measured 3.099 ms/token (20B) and 4.478 ms/token (120B). The remaining gain comes from task placement and cross-layer PDL overlap.

The plans place the gate's `(t, 0, 0)` tasks. When the gate's router is split (`ROUTER_SPLITS`: 4 tasks a token on 20B, 8 on 120B), `place_router_splits` puts the other splits on SMs with no task from o_proj onward before their first W13 task. Same H100, same runs (200/200 tokens identical to the reference):

| Model | Unsplit gate | Split router | + weights preloaded before the wait |
| --- | ---: | ---: | ---: |
| GPT-OSS-20B | 3.053 ms/token | 2.964 ms/token | 2.950 ms/token |
| GPT-OSS-120B | 4.387 ms/token | 4.152 ms/token | 4.122 ms/token |

Each layer kernel also prefetches the first `L2_PREFETCH_MB` (12) MB of its QKV weight into L2 at its start (`StaticMegakernel.l2_prefetch_weights`), on the SMs that start while the previous kernel finishes. Same H100, same runs (200/200 tokens identical to the reference):

| Model | No prefetch | 8 MB | 12 MB | 16 MB |
| --- | ---: | ---: | ---: | ---: |
| GPT-OSS-20B | 2.834 ms/token | 2.792 ms/token | 2.791 ms/token | 2.797–2.800 ms/token |
| GPT-OSS-120B | 4.132–4.135 ms/token | 4.061–4.064 ms/token | 4.060–4.061 ms/token | 4.072 ms/token |
